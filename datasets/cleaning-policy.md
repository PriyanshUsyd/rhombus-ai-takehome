# Cleaning policy — APPROVED

Status: **APPROVED 2026-10-03**, before the first Rhombus run. This file is the ground truth for what a correct output looks like. The validator derives its expectations from **the input + this policy**, never from the Rhombus output.

Input: `datasets/baseline.csv` (generated by `scripts/generate_datasets.py`, seed 20261003). Defect counts and affected ids are listed in `datasets/baseline.manifest.json`.

## 1. Input contract

| Column | Meaning | Clean input form |
|---|---|---|
| `id` | Transaction id, unique per transaction | integer |
| `name` | Customer name | `First Last`, Title Case, single space |
| `email` | Customer email | lowercase, no surrounding spaces |
| `country` | Customer country | one of: Australia, New Zealand, United States, United Kingdom, Canada, India, Singapore, Germany |
| `price` | Unit price | decimal with 2 dp, no symbol |
| `qty` | Quantity | positive integer |
| `total` | `price × qty` | decimal with 2 dp |
| `transaction_date` | Transaction date | `YYYY-MM-DD` |
| `status` | Transaction status | one of: `completed`, `pending`, `refunded`, `cancelled` |

An empty field counts as a missing value.

## 2. Order of operations

1. **Trim** leading/trailing whitespace on every field; collapse repeated internal spaces in `name`.
2. **Normalise** formatting (email lowercase, casing of name/country/status, strip `$` from price, convert dates to ISO).
3. **Deduplicate** on the key (section 3).
4. **Validate** each surviving row; apply reject / repair / null (section 4).
5. **Write** output with the target formats (section 5).

Normalising before deduplicating is what makes the email near-duplicates collapse.

## 3. Deduplication

- **Dedup key:** `id`.
- **Missing or non-integer `id` → reject the row** (added 2026-10-03). Such a row cannot be deduplicated, so it is rejected before dedup. The baseline has none, so the expected counts are unchanged.
- **Email matching:** emails are compared after trimming whitespace and lowercasing. Email is *not* part of the dedup key.
- **Survivor rule:** keep the **first occurrence in file order**; drop later rows with the same `id`. In the baseline every duplicate is a copy of a clean row (exact copies, or copies whose email differs only by case/whitespace), so after normalisation the survivor is the same whichever copy is kept.
- **Not duplicates:** rows with different `id`s that share a normalised email (the same customer on different transactions). They must **all be kept**. The `email_case_whitespace_variant` rows test this: a pipeline that deduplicates by email would wrongly drop them.

Reasoning in short: a field that is derivable or purely cosmetic gets **repaired**. A descriptive field that is missing or invalid becomes **null**, and the transaction is kept. A row whose money or date cannot be trusted is **rejected**.

### Total rule (exact decimal comparison)
`expected_total = price × qty`, computed in exact decimal arithmetic (never float) and rounded to 2 dp (round half up). A row is a `total_mismatch` only if `total` (as a decimal) ≠ `expected_total`. Example: `12.34 × 3 = 37.02` → total `37.02` passes and `37.020` passes, but `37.03` is rejected. The same `expected_total` is used to fill a missing `total`.

### Date parsing (explicit, never inferred)
Accepted input formats, in this order: `YYYY-MM-DD`, `DD Mon YYYY`, `Month DD, YYYY`, `YYYY/MM/DD`, `DD/MM/YYYY` (the last only when the first number is > 12, which makes it unambiguous). A slash date where both numbers are ≤ 12 is ambiguous and is **rejected**; the baseline contains none. Anything else is rejected.

## 5. Target output format

- Same 9 columns, same order, header row, CSV, UTF-8.
- `id`: integer. `qty`: integer.
- `price`, `total`: plain decimal with exactly 2 dp, `.` separator, no symbol or thousands separator. Money is compared with `Decimal`, never float.
- `transaction_date`: `YYYY-MM-DD`.
- `name`: Title Case, single-spaced. (All baseline names are simple ASCII `First Last`, so Title Case is unambiguous.)
- `email`: lowercase, trimmed.
- `country`: canonical name from the allowed list.
- `status`: lowercase, from the allowed set.
- Null = empty field.
- Row order: not significant. The validator compares on `id`.

## 6. Expected outcome on the baseline (derived from manifest + this policy)

| Step | Rows |
|---|---|
| Input rows | 250 |
| Removed by dedup (10 exact + 6 near) | −16 → 234 unique ids |
| Rejected (2 missing price + 2 missing qty + 2 missing date + 2 non-numeric price + 3 non-positive qty + 2 impossible date + 3 total mismatch) | −16 → **218 output rows** |

The 218 output rows break down as:

- **35** repaired rows (6 email variant + 5 name + 5 country + 5 status + 3 price `$` + 8 date format + 3 missing total);
- **19** rows kept with a null (3 each missing name/email/country/status + 3 malformed email + 2 unknown country + 2 unknown status).

Check: 164 + 35 + 19 + 16 rejected = 234 unique ids.

## 7. Decisions (approved 2026-10-03)
1. **Rejected rows are dropped** from the output file, with no separate reject file. The validator reconciles the count.
2. **Malformed email → null** (row kept).
3. **Unknown status → null** (row kept).
4. **`total_mismatch` → reject**, comparing `total` against `price × qty` rounded to 2 dp in exact decimal arithmetic (see total rule), so float noise cannot cause false rejects.
5. **Survivor = first occurrence** in file order.
